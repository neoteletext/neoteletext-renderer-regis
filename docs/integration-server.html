Plan: ReGIS in the NeoTeletext server

A proposal for carrying ReGIS pages through the Rust WebSocket server (neoteletext-app-server). Nothing here is built. It was written on 14 November 2026 from a reading of the server at commit 8d0c7b3, the protocol document in neoteletext-common, and the TypeScript and Python kits.

What the server does today

  • One format. A channel's program (a separate process speaking JSON lines, protocol 7) sends page messages; the runtime (crates/teletext-runtime, no_std, no I/O) encodes them with the engine as 42-byte teletext packets and sends them in binary WebSocket messages. There is no content-type field anywhere.
  • The downstream rule. DEC-1459: "Downstream to a receiver is a T42 stream, and nothing else." What is not page content "travels as records in packet 4/31 on data channel 12", and a record type a receiver does not know is skipped by its type byte. Types 1 to 12 are in use; a record body is at most 8,192 bytes.
  • Negotiation. HELLO and WELCOME carry a capability bit set; bits 23 and up are free. A sender uses a new feature "only when both sides set its capability".
  • Checks. Every packet sent passes the engine's is_valid_stream_packet; every program message is read strictly against protocol/schema-7.json, and an unknown field refuses the whole line.
  • Rules for change. Web-protocol reading and record encoders belong in the engine, which the server pins by git revision; wire vectors live in neoteletext-common/wire-vectors.tsv; a feature that adds an input or output needs a proposal, a security analysis and the owner's adoption decision first; every library needs approval by name.

Design (options A and C together)

1. Capability

Capability bit 23, REGIS. The browser sets it in HELLO when it can draw ReGIS; the server agrees it in WELCOME. Without it the server sends the mosaic fallback and no ReGIS records.

2. Program protocol (version 8)

One new program-to-server message beside page:

{"type":"regis","page":"1a0","sub":0,"data":"<base64 of ReGIS commands>","append":false}
  • data is bare ReGIS commands, not a device control string. At most 262,144 bytes decoded (a dense screen is 20 to 40 KB).
  • append: false replaces the page's picture; append: true adds commands to it, for animation and live updates. The server keeps the whole stream for the page so that a receiver selecting it later gets the picture from the start.
  • The page keeps an ordinary teletext row 0 (header) from a page message so that page numbers, links and sub-pages work as today. The ReGIS picture replaces rows 1 to 24 on receivers that draw it.
  • New refusal rules: regis_too_long, regis_bad_byte, regis_limit.
  • Changes: a ProgramMessage::Regis variant and MessageType entry (protocol.rs), its reader (protocol/read.rs), its checks (protocol/check.rs), its action (channel.rs, beside send_page), PROTOCOL = 8, protocol/schema-8.json, and the copies of the schema in the TypeScript and Python kits. The kits gain a regis() call.

3. Checking what a program sends

  1. Bytes. Only printable ASCII, the Latin-1 right half, CR, LF, BS and HT. ESC and the C1 controls are refused, so no control string can hide inside.
  2. A trial render. The runtime feeds the stream to a regis::Terminal on a scratch Screen. If the library reports LimitReached the message is refused with regis_limit: a receiver would hit the same limit, and a microcontroller receiver should never be sent work a desktop could barely afford. The trial also produces the picture for the fallback.
  3. Reports. Event::Reply and LocatorRequest from the trial are discarded. Nothing a stream asks to be reported is sent anywhere in the first version.
  4. Waits. S(T n) is honoured by the receiver, within its own ceiling; the server does not pace.

The trial render costs CPU on the server: at most the library's work allowance, about 16 million pixel visits plus 256 for each byte, a few tens of milliseconds for a full message. The existing rate limits on program messages apply.

4. The record

Record type 13, REGIS, on data channel 12, in the engine's neoteletext-web/src/records/regis.rs beside the other encoders:

FieldSizeMeaning
page2 bytesMagazine and page number, as in the LINKS record.
sub2 bytesSub-page.
generation2 bytesChanges when the picture is replaced, so a receiver can tell a new picture from more of the old one.
offset4 bytesWhere in the page's ReGIS stream these bytes begin. Zero with a new generation means "start again on a blank screen".
bytesup to 8,176ReGIS commands.

A long stream is cut into several records at any byte: the renderer accepts a stream cut anywhere (tests/streaming.rs). The server sends the records after the page's teletext packets when a connection selects the page, and sends only the new bytes on an append. The per-connection baseline (Shown in channel.rs) gains the generation and offset last sent.

Wire vectors for the record are added to neoteletext-common/wire-vectors.tsv, copied into the engine, and the server's pin is moved in a commit of its own, as DEVELOPMENT.md section 11 requires.

5. The fallback

For a connection without the capability, the runtime turns the trial render's 800×480 picture into teletext rows 1 to 24 with the engine's neoteletext-image converter and sends them as an ordinary page. The picture is 5:3 and the page area 40×24 cells, so it is letterboxed. An append re-renders and sends changed rows, which the existing changed-rows logic already does.

6. Dependencies

  • regis as a git dependency at one pinned revision, with default-features = false, added to deny.toml's allow-git. It is no_std, has no dependencies and does no I/O, so it fits the runtime crate and builds for wasm32-unknown-unknown (Cloudflare).
  • The font: the server needs one for the fallback picture only. It would be the same font data the browser uses, embedded in the server binary.

7. Input

Pointer and key events already reach programs stamped with the page. A program drawing ReGIS needs pointer positions in picture pixels; the input event's optional pixel position can carry them once the browser plan's mapping is agreed. No server change beyond passing them through.

Security analysis to write before building

  • The trial render as a CPU and memory cost per program message, and what a hostile or broken program can cost the server.
  • The record as a new downstream payload: size, rate, and that an old receiver skips it (a wire vector proves it).
  • That no report or reply path exists, so the answerback class of attack cannot occur.
  • The fallback path: the converter's cost and its output passing is_valid_stream_packet.
  • A fuzz target for the new program message and for the record encoder.

Order of work

  1. Owner's decision: adopt options A and C; amend DEC-1459's record list; allocate record type 13 and capability bit 23. Requirements recorded in rdm for the engine, server, kits and common.
  2. neoteletext-common: PROTOCOL.html sections for the record, the capability and protocol 8; wire-vector rows.
  3. neoteletext-engine: the record encoder and decoder, the capability constant, the wire-vector copy.
  4. neoteletext-app-server: move the engine pin; add the regis pin; the message, checks, trial render, record sending, fallback; schema 8; tests and fuzz targets.
  5. Kits: schema copies and the regis() call; one demonstration channel.
  6. Browser: see the browser plan. Until it is done every receiver gets the fallback, so the server side can ship first.

Questions for the owner

  1. Is a mosaic fallback wanted, or should a receiver without ReGIS simply see the page's teletext rows as the program sent them?
  2. Should a ReGIS page be a page in the ordinary numbering (as proposed), or a separate kind of resource?
  3. Is 262,144 bytes the right ceiling for one page's stream?
  4. Should stream replies (R commands) ever reach the program? The proposal says no.
