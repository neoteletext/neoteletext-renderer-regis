Plan: ReGIS in the NeoTeletext browser

A proposal for showing ReGIS pages in the native browser (neoteletext-browser). Nothing here is built. It was written on 14 November 2026 from a reading of the browser at commit 526e695 and its architecture document, and it depends on the server plan for how ReGIS arrives.

What the browser does today

  • Processes. A fetcher per web channel reads the network; the trusted core passes bytes on unread; a decoder per channel, with no rights, parses them with the teletext engine and renders; the interface process draws frames and parses no outside data.
  • One picture shape. The decoder calls the engine's render_screen into 480×500 palette indices of at most 32 colours. The frame message (protocol/src/frame.rs) rejects any image that is not exactly 480×500, and a message is at most 256 KB. The size 40×25 cells of 12×20 dots is a constant in interface-core/src/canvas.rs, the frame reader, the painter, the input bounds and the decoder's buffers.
  • One format. Records DEC-1762, REQ-4437, REQ-5350 and REQ-722 say the browser opens T42 and TTI only and that other readers "MUST NOT be compiled into the browser's decoder"; a test asserts it. REQ-1645 and REQ-5558 say a page is drawn in 40×25 at every level. NAPLPS is not in the browser either.
  • Input. A pointer position is a page cell and a dot within the 480×500 image, never a screen coordinate; the event type already has an optional pixel pair.
  • Time. At most one frame per 20 ms field. Flash is done by the decoder rendering again; the interface has no clock for pictures.
  • Rules. The engine is a git dependency at one pinned revision; every library needs approval by name; every reader of outside input has a fuzz target and a security document; untrusted bytes are parsed only in rightless processes.

Design

1. Where the renderer runs

In the decoder process, beside the engine. It already holds the channel's bytes, has no rights, and is the only place outside data is parsed. regis is added as a git dependency at one pinned revision (and to deny.toml's allow-git). It is no_std, has no dependencies, no unsafe code and no I/O, which is what the decoder's rules ask of the engine.

2. How a page becomes a ReGIS page

Never by guessing from the bytes. A page is ReGIS when the decoder has received ReGIS records for it (record type 13 in the server plan). The engine decodes the record frame; the decoder keeps, for each page and sub-page, a regis::Terminal, a regis::Screen, the generation and the offset reached, and feeds each record's bytes as they arrive. A new generation starts a new terminal and a blank screen. The browser announces capability REGIS in HELLO.

For static channels, a file NNN.regis beside NNN.tti would be the same stream in a file; that is a second step and needs its own media type decision.

3. A frame with a shape

The frame message gains a shape: teletext (480×500) or ReGIS (800×480). The reader checks the image against the size its shape names, instead of one constant.

  • Size. A raw ReGIS frame is 384,000 bytes, over the 256 KB message limit. The frame format already has run-length and changed-area forms; a ReGIS picture is mostly flat colour, so runs are far smaller (the densest sample here is under 40 KB). A frame that still does not fit is sent as bands in several messages. The limit itself is not raised.
  • Colours. Sixteen, within the existing limit of 32. The palette comes from Terminal::palette() with each frame, so a colour-map change (S(M…)) is a palette change and no pixel is resent, as with teletext flash.
  • Changes. The decoder compares the new screen with the last one sent and sends changed rows, as it does for teletext.

4. Drawing it

The painter keeps a pixmap per page; for a ReGIS page it is 800×480. Two ways to place it:

OptionPlacementVerdict
AInside the same page rectangle a teletext page gets, scaled evenly and centred, the remainder filled with colour 0 of the picture's map.Recommended. Window layout, tabs and chrome do not change with the kind of page; REQ-1645's "predictable screen resolution" holds for the window.
BThe page area takes the picture's own 5:3 shape.The window would change shape between pages.

A VT340's pixels are close to square, so the picture is shown 5:3 with nearest-neighbour scaling, as teletext pages are. Row 0 of the teletext page (the header) stays above the picture, drawn by the engine as now; the picture takes the area of rows 1 to 24.

5. Time

Event::Wait from the renderer pauses that page's feeding: the decoder stops feeding bytes, renders a frame, and asks the core for a wake-up after the wait, exactly as it does for flash. Ceilings: the library allows a minute a call; the decoder adds its own per-page ceiling (proposed: 10 seconds a wait, and animation stops when the page is not selected). Frames stay at one a field at most.

6. Input

For a ReGIS page the pointer event carries the pixel pair in picture coordinates, 0 to 799 and 0 to 479, in the field the event already has; the cell and dot are derived from them (cell width 20, height 480/24 = 20) so that programs written for cells keep working. The trusted core's check that the dot lies in its cell is extended to the picture's cell size. This needs a line in the input protocol document and wire vectors.

7. What is not done

  • Replies. Event::Reply and LocatorRequest are dropped in the decoder. A ReGIS stream can make the browser send nothing.
  • Macrograph reports stay off.
  • The graphics cursor is not drawn; the browser's own pointer is the cursor.
  • Fonts. One font file is embedded in the decoder, the same data the server uses for its fallback. Whether the VT340 ROM font or DEC's VWSVT0 may be shipped needs the owner's decision; the engine allows only Noto Teletext to be compiled in (DEC-1761), so the alternative is an original font drawn for the purpose.

Records to change first

  • A decision that the browser draws ReGIS, amending DEC-1762, REQ-4437, REQ-5350 and REQ-722 (formats the decoder may read) and the test in native/decoder/src/engine/tests.rs that asserts only two formats.
  • A decision on placement (section 4) against REQ-1645 and REQ-5558.
  • Requirements for the frame shape, the size rule, the wait ceiling, the input mapping and the dropped replies.
  • A regis-security.md for the feature, as each feature has, and a fuzz target feeding the record path into the renderer.

Order of work

  1. The server plan's steps 1 to 3 (decision, protocol document, engine record decoder).
  2. Browser records and the security document.
  3. protocol: the frame shape and its reader; fuzz target.
  4. decoder: the regis pin, per-page terminals, record feeding, frames, waits.
  5. interface-core, draw-vello, draw-embedded: the second pixmap size and placement.
  6. Input mapping in protocol, the trusted core and the input document.
  7. Golden tests: a set of ReGIS pages rendered through the whole pipe, compared by checksum as the teletext rasters are.
