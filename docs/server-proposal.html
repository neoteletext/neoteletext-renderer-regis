A ReGIS application platform

A proposal for building interactive applications on the NeoTeletext ReGIS renderer: an extended client that keeps the picture as a retained structure of named objects, and a Rust server that manages client connections over websockets, exposes a strongly typed API, carries all the universal logic, and runs application code written in TypeScript, Python or any other language. This document gives the background, the research the design rests on, every part of the design, the problems it must solve and how it solves them, and what remains to be decided.

Status. A design proposal; none of the platform described here is built. Figures marked measured come from the existing renderer and the test corpus. Figures marked estimated are reasoned from the renderer's behaviour and must be confirmed by a prototype. This revision replaces an earlier version that kept the client as a plain VT340 ReGIS terminal and put all the intelligence in the server; section 33 explains what changed and why.

1. Purpose and scope

NeoTeletext has a renderer for ReGIS, the vector graphics language of Digital Equipment Corporation's VT340 terminal. It is a Rust library with no dependencies that takes ReGIS bytes and draws them on an 800 by 480 screen of sixteen colours exactly as the terminal did, hardened against hostile input. Around it are a command-line renderer, a compact painting encoder that makes detailed pictures small, and a minifier that rewrites ReGIS shorter without changing what it draws.

A renderer displays pictures. To build applications on it, such as industrial dashboards, trading screens, strategy games, maps and forms, something must turn what users do and what data arrives into changes on screen, efficiently and reliably, over a network. This document proposes that something: a platform made of an extended client renderer and a server.

The platform has five fixed requirements:

  1. A Rust server manages the client renderers, which connect to it over websockets.
  2. The server exposes a very strongly typed API.
  3. Universal logic is built into the server: everything that is the same for every application is written once, in Rust.
  4. Application logic is written in TypeScript, Python or any other language.
  5. Keypresses, mouse events and touch events travel from the client through the server to application code.

Out of scope: the design of particular applications, the client's own surrounding user interface, and the NeoTeletext broadcast path that carries ReGIS inside teletext data records.

2. Governing decisions

These decisions were made deliberately and shape everything that follows.

  • We control the platform, end to end. The client renderer is ours, and it will be extended freely. There is no capability negotiation and no fallback to plain VT340 ReGIS for other displays. Compatibility with real VT340 terminals or other ReGIS implementations is not a goal.
  • Limits suit this platform, not vintage hardware. Every new feature is bounded, generously, to protect the client from a faulty server, not to imitate a 1987 terminal.
  • No session-resumption machinery in the client. No sequence acknowledgements, state hashes or resynchronisation protocol. A client that reconnects is sent its whole picture again.
  • No raster images, ever. Everything on screen is drawn from vector commands.
  • No local animation. Nothing moves or changes on screen unless the server sends a change.
  • No separate text layer or font system. Text is ReGIS text, in ReGIS's own and loadable character sets.
  • Applications implement behaviours such as scrolling themselves, using the primitives the platform provides.
  • No copied code. Everything is written for this project; outside work informs the design only.

3. Background: what ReGIS is

ReGIS, the Remote Graphics Instruction Set, was introduced by DEC in the early 1980s for its graphics terminals, the VT125, VT240 and VT241, and the VT330 and VT340. A host computer sent plain text commands such as P[100,200]V[300,200] (move to a point, draw a line to another) and the terminal drew them. The VT340 displayed 800 by 480 pixels in sixteen colours chosen from a palette of 4,096.

The language has commands for position (P), vectors (V), curves, circles and arcs (C), polygon fill (F), text (T), write controls (W: colour, line pattern, writing mode, plane mask, shading), screen control (S: erase, colour map, scrolling, pages), loadable character sets (L), macrographs (@, stored command sequences) and reports (R). The renderer implements all of it, following DEC's programmer reference manual and checked against screen captures from a real VT340: three of four reference pictures match pixel for pixel, and the fourth differs only along the edges of circles.

4. The constraints of plain ReGIS

Plain ReGIS has six properties that make applications hard to build. The platform exists largely to remove them.

4.1 It remembers nothing

Every command ends as pixels in the screen's memory. The terminal keeps no record of which command drew which pixel and no list of objects.

4.2 Nothing can be removed

Because nothing is remembered, nothing can be deleted. To make something disappear, a program must draw over it with whatever should be there, which means knowing what was underneath.

4.3 The screen is pixels, not cells

Unlike a character terminal, ReGIS has no grid. Changing part of the screen has no natural unit, and the cost of a change depends on what lies there.

4.4 There is no clipping

ReGIS cannot restrict drawing to a rectangle. A shape drawn to repair one area draws all of itself.

4.5 Scrolling moves the whole screen

The scroll command moves the entire picture; a list inside a panel cannot be scrolled.

4.6 Input is request and reply

The terminal reports the pointer only when asked, and reports coordinates, never what was pointed at.

4.7 Bytes are the cost of everything

Early paintings made for the test corpus with a naive method were 5 to 11 MB of ReGIS each; made carefully they are 30 to 150 KB (measured). Every byte crosses the network.

5. The writing modes

ReGIS's own tools for working within these limits are its writing modes, set with W:

ModeCommandEffectUse for removal
OverlayW(V)Draws the foreground where the line pattern is on; the defaultNone
ReplaceW(R)Draws foreground where the pattern is on and background where it is offReplace-mode text clears its own cell
ComplementW(C)Inverts the colour bits of every pixel coveredDrawing the same thing again restores the picture exactly
EraseW(E)Draws in the background colourRubs a shape out, cleanly only on a plain background

Two related controls: the negative pattern W(N1) inverts the line pattern, and the plane mask W(F…) restricts drawing to chosen bit planes. Complement within one plane flips only that plane's bit, giving a predictable colour and exact removal.

In plain ReGIS these modes are essential workarounds. In the platform proposed here, removal is handled by retained objects, so the modes return to being drawing styles: replace mode for dither fills and replace-mode text, complement for deliberate inversion effects. They remain fully available inside objects.

6. How ReGIS was programmed originally

Programs on VAX and PDP-11 computers printed ReGIS command strings built with string formatting in FORTRAN, BASIC, Pascal or C, or used graphics libraries with ReGIS output drivers, such as implementations of GKS. At 9,600 or 19,200 baud, programmers developed a craft of economy: draw static parts once and update only changing values, erase by drawing over, define repeated symbols as macrographs, animate and highlight through the colour map, draw cursors in complement mode, and use the second page for flicker-free updates. Input was request and reply; the program worked out what had been pointed at from its own records. In effect the programmer was the system that remembered the screen and computed the smallest change. The platform moves that memory into the client, where it belongs.

7. What the research shows

The design rests on sixty years of systems that sent graphics to a display device, often over a slow link. Their lessons converge.

7.1 Display files and display processors (1963 to the 1970s)

Ivan Sutherland's Sketchpad (1963) kept a display file, the picture as data separate from the screen, and introduced masters and instances: a drawing defined once as a master and placed many times as instances, so that changing the master changed every instance. Sketchpad's display file also recorded, for each displayed spot, the address of the element responsible for it, so the program always knew what was where. Vector display processors such as Evans and Sutherland's LDS-1 (1969) and later Picture System ran from a display list, a program of drawing instructions with subroutine calls for repeated symbols. Their display files were organised into segments that could be double-buffered, so that the old version of a segment stayed visible until the new one was complete. Lesson: keep the picture as structured data, named objects, masters and instances, wherever it is drawn, and change it by editing the data; update each object atomically.

7.2 Graphics standards and terminals: GKS, PHIGS, Tektronix

The GKS standard and Tektronix's raster terminals of the 1980s (the 4105, 4107 and 4115) kept named segments: groups of drawing commands with attributes for visibility, highlighting, detectability for picking, display priority and transformation. The terminal or library redrew whatever a change exposed, and could report which segment the user pointed at. PHIGS added hierarchical structures: structures calling structures, with transforms inherited. Lesson: the useful operations on retained objects are well known (create, delete, show, hide, move, transform, priority, highlight, pick), and hierarchy with inherited attributes keeps complex scenes manageable.

7.3 Overlapping windows: Pike's layers and the Blit (1983 to 1984)

Rob Pike's layers gave each program its own overlapping region on a bitmap terminal, with drawing fully isolated from other programs even where regions overlapped. The Blit terminal could also load programs from the host and run them locally. Lesson: clipping each region to its own window, in its own coordinates, is what makes independent regions safe. Downloading code to the display is a step this platform does not take.

7.4 The X Window System: from hints to compositing

X offered backing store and save-unders (keeping obscured pixels so they could be restored) as hints a server could ignore; applications always had to redraw when told a region was exposed. The X.Org server later dropped these features in favour of compositing: each window renders off screen, a damage extension reports what changed, and a compositor assembles the screen. X's Render extension took its compositing model from Plan 9's draw device and its operators from Porter and Duff's 1984 algebra. A Silicon Graphics note compared overlay planes with save-unders: overlay planes avoid damage to underlying windows in hardware at little cost, while save-unders and backing store carry heavy software overhead. Lesson: saving pixels under things was a stopgap the field abandoned; retained structure with damage tracking won.

7.5 Plan 9's draw device

Plan 9's display device holds resources in its own storage, referenced by numeric ids that clients allocate and draw into, and composites them with a chosen operator. Lesson: a client-held store of numbered resources, referenced by small ids chosen by the program, is simple and efficient.

7.6 Thin-client research (1999 to 2005)

SLIM, the Sun Ray protocol studied at Stanford and Sun (SOSP 1999), used a small set of low-level 2D primitives pushed from the server to a minimal console. THINC (Columbia, SOSP 2005), inspired by SLIM, used a few simple primitives (raw, copy, solid fill, pattern fill, bitmap) and added offscreen drawing awareness and command buffering and scheduling. Microsoft's RDP sends drawing orders and keeps client-side caches referenced by index: glyphs, brushes, bitmaps and offscreen surfaces. Lessons: caches of reusable things referenced by id save enormous bandwidth; coalescing updates before sending matters. These systems leaned on raster copies because they mirrored desktops of pixels; a platform that controls its own content does better with retained vector objects.

7.7 Flash and SWF

Macromedia Flash's SWF format kept a dictionary of shapes defined once by id and a display list of instances at explicit depths; each frame placed, modified and removed instances, and the player redrew dirty regions. ActionScript 3 exposed the display list as a typed tree with DOM-style events. Lesson: the retained model again, proven at internet scale, with depth as the ordering primitive. Flash also shows the cost of a client that runs code: its player was a notorious security problem.

7.8 Hardware sprites

The home computers of the 1980s drew sprites in video hardware over the background at a position, never writing them into the background, so moving a sprite needed no erasing. Lesson: objects composited rather than burned into the picture never need undoing.

7.9 Curses and modern terminal libraries

The curses library (about 1980) kept a record of what the terminal showed and computed the cheapest update on each refresh. Modern libraries (Ratatui, Bubble Tea, Textual, Ink, notcurses) keep a double-buffered cell grid with a diff underneath and offer immediate-mode, Elm-style, retained-widget or React-style models above it, and many use the terminal's synchronized-output mode so frames are atomic. Lesson: applications may describe whole screens freely when something underneath computes the difference; every cause of change can be a message; frames should be atomic.

7.10 Live server user interfaces

React and Elm describe interfaces as functions of state; live server interfaces such as Phoenix LiveView keep a session per connection, re-render on events and send diffs to a browser. Lesson: the server-held session with event-driven updates is a proven shape for networked interactive applications.

8. The synthesis: a retained display file

Across sixty years one answer recurs: keep the picture as a retained, structured set of named objects in the display device, and let the device redraw damage itself. Masters and instances, hierarchy, depth, visibility, picking, atomic updates and caches by id all follow from it. The pixel-level answers (bitmap layers, save-unders, rectangle copies) were stopgaps or artefacts of mirroring pixel desktops.

Because the platform controls both ends, it can take the object answer directly. The client renderer keeps a display file: every object, its contents in ReGIS, its depth, place in a hierarchy and attributes. When anything changes, the client repaints the damaged area from the display file, clipping internally, which its own rasteriser can do even though ReGIS never exposed clipping. Every constraint in section 4 disappears:

9. Requirements

9.1 Functional

  1. Clients connect to the Rust server over websockets and are associated with application sessions.
  2. Each client's screen always shows its application's current view.
  3. Only changes are sent: object definitions, edits, attribute changes, deletions.
  4. Applications describe and change screens through a strongly typed API.
  5. Applications are written in TypeScript, Python or any language speaking the protocol.
  6. Keys, mouse and touch reach applications as typed events naming the object concerned.
  7. Applications may change screens at any time, not only in response to input.
  8. A client that reconnects receives its whole picture again.

9.2 Non-functional

  1. Determinism: the client draws a given display file identically every time, on every build.
  2. Economy: interactive changes cost tens of bytes; the platform never resends what the client holds.
  3. Isolation: a faulty application cannot crash the server or harm a client.
  4. Safety: client and server treat their inputs as untrusted and bound every allocation.
  5. Scalability: tens of thousands of sessions per server.
  6. Latency: processing on server and client well under the network round trip.

10. Architecture overview

  CLIENT RENDERER                      RUST SERVER                                APPLICATION
  (browser or native)                                                             (TypeScript, Python, any)
                          websocket                          local socket
  display file    <--- object operations ---   +-----------------------+   <--- transactions of typed operations ---
  damage repaint  ---- events: object picked -> |  per session:         |   ---- events: key, pointer, touch ----->
  ReGIS rasteriser                              |   display-file mirror |   ---- session opened / closed -------->
                                                |   validation, limits  |
                                                |   id allocation       |
                                                |   event routing       |
                                                |   coalescing          |
                                                +-----------------------+

The client holds the display file, rasterises it with the existing renderer, repaints damage, picks objects under the pointer, and sends input events. It contains no application logic and runs no animation.

The server holds, per session, a mirror of the client's display file (objects only, no pixels), validates and limits everything, allocates ids, routes events, coalesces changes, and translates the typed API into client operations.

The application is an ordinary program that receives typed events and responds with typed operations. It never sees ReGIS or the websocket.

One interaction:

  1. The user taps a button. The client finds the topmost detectable object under the touch and sends an event naming it.
  2. The server validates the event, resolves the object id to the application's name for it, and forwards a typed event.
  3. The application updates its state and replies with a transaction: for example, set the button's highlight, replace a text object's string, append a point to a series.
  4. The server validates the transaction, applies it to its mirror, and sends the equivalent client operations in one message.
  5. The client applies them atomically and repaints the damage once.

11. The client: the display file

The display file is the client's retained model of the screen. It holds masters (definitions, never displayed directly), objects (things displayed: drawings, instances of masters, groups, viewports, text and series objects), and for each object its depth, parent, transform, attributes and contents. The screen is always the display file, rasterised.

The client's job is narrow and exact:

  • apply operations to the display file atomically, in transactions;
  • repaint the damage each transaction causes;
  • pick the object under the pointer and send events the server has asked for;
  • enforce the limits.

It never decides anything about the application. Determinism is essential: the same display file must produce the same pixels on every build of the client, which is what conformance tests check.

12. Objects, masters and instances

12.1 Named objects

An object is opened by id, filled with ordinary ReGIS drawing commands, and closed. Ids are small integers allocated by the server. Operations: create, delete, rename (change id), and redefine (replace contents, section 16). Inside an object, all of ReGIS is available, including the writing modes, loadable character sets and macrographs.

12.2 Masters

A master is a definition, never drawn itself. It holds ReGIS drawing commands in its own local coordinates. Redefining a master changes every instance of it. Masters are the platform's cache of reusable shapes: a star glyph, a ship, a valve symbol, a button, an emblem.

12.3 Instances

An instance places a master in the display file, with its own position, transform, depth, attributes and colour remap. Hundreds of identical markers cost one master and a few bytes each.

12.4 Colour remapping per instance

An instance may map its master's palette indices to others. One ship master drawn in eight faction colours; one button master in normal, pressed and disabled colours; one valve symbol in running, stopped and fault colours. Colour remapping makes state changes a single attribute change.

13. Depth, hierarchy and transforms

13.1 Depth

Every object has an explicit depth within its parent: later depth draws over earlier. Objects can be inserted at a depth, raised and lowered. Drawing order is data, not history, as in SWF and GKS.

13.2 Hierarchy

Groups contain objects and other groups. Position, visibility, colour remapping and highlight are inherited. Moving a group moves everything in it; hiding it hides everything in it. Hierarchy depth is limited (section 19).

13.3 Transforms

Transforms are exact on the pixel grid: translation by integers, scaling by integer factors, mirroring, and turns in 90-degree steps. These keep rendering deterministic and identical across builds. Arbitrary rotation and fractional scaling are excluded because they lose exactness; they can be considered later if a real need appears.

13.4 Visibility

Every object can be shown or hidden. Hiding repaints what lies beneath; showing repaints the object. Combined with depth, visibility replaces every use the earlier design had for erasing.

14. Viewports and masks

14.1 Viewports

A viewport is a group with a clip rectangle on the screen and an inner coordinate offset. Its children are drawn in the viewport's own coordinates, shifted by the offset and clipped to the rectangle. Panels, lists, map views, documents and dialogs are viewports. This is GKS's viewport and Pike's layer, in retained form.

Scrolling is implemented by the application: it changes the viewport's offset, one small operation, and the client repaints the viewport's area from the display file. For long lists the application adds and removes child objects as they come into and leave view; the platform does not scroll by itself and does not animate.

14.2 Masks

An object may serve as a clipping shape for a group: its children are drawn only inside the mask's filled area. A round gauge face, a porthole, a map region. Masks are on-or-off clipping, the useful part of Porter and Duff's "in" operation; sixteen indexed colours have no transparency to blend.

15. Damage repaint in the client

When a transaction changes the display file, the client works out the damaged area: the old and new bounds of every changed object, transformed and clipped by their ancestors. It then redraws only the objects intersecting that area, in depth order, with drawing clipped internally to the damage. Damage is tracked as a set of rectangles, merged when they overlap or when merging is cheaper.

This is invisible in the protocol and is what makes the whole model cheap: deleting, hiding, moving, recolouring and redefining objects all cost only the area they affect. It also replaces every pixel-level technique of the earlier design: there are no shadow pixels on the server, no replay with transitive closure, no overlay planes and no save-unders.

Internal clipping is exact: the rasteriser decides per pixel whether a pixel lies in the damage before writing it, so an object redrawn inside a damaged rectangle produces exactly the pixels it would produce in a full redraw. Patterns, dither tiles and text cells are anchored to the screen as they are now, so partial redraws match full ones.

Repaint cost is bounded per transaction (section 19); a transaction that would exceed it is rejected by the server before it is sent, because the server computes the same damage from its mirror.

16. Transactions and editing

16.1 Transactions

Operations arrive in transactions: begin, a batch of operations, commit. The client applies the whole batch to the display file and repaints once at commit. No partly applied state is ever shown. This replaces page flipping for updates and gives the effect of the double-buffered segments of the display processors.

16.2 Edit in place

Redefining an object replaces its contents atomically while keeping its id, depth, parent, transform, attributes and children. Changing a gauge's needle, a button's label or a chart's axis is a redefine, never an erase and redraw.

17. Text and series objects

17.1 Text objects

A text object holds a string, a position, a ReGIS text size and direction, a character set and a colour. "Set string" replaces the string; the client handles clearing and redrawing through damage repaint. This is ReGIS text made retained, not a new font system: the characters are those of the built-in and loadable sets.

17.2 Series objects

A series object is a polyline with operations to append a point, drop the oldest point, and replace a point, plus a line pattern and colour. Trend lines, charts, sensor traces, price histories and fleet routes update by a point at a time. For dashboards this is the single largest saving: a moving trend costs a few bytes per sample instead of a redrawn chart.

18. Input: picking, hit shapes, interest, highlight

18.1 Pushed events

The client sends input as it happens: keys with modifiers, pointer movement, presses and releases, wheel movement, and touch points. Pointer movement is coalesced to a rate the server sets.

18.2 Picking by object

Objects carry a "detectable" attribute. Every pointer and touch event reports the topmost detectable object under it, the path through the hierarchy to it, and the position in that object's local coordinates. Applications never do geometry.

18.3 Hit shapes

An object may declare a hit area separate from its drawing, for example a padded rectangle around a small target, so touch works on small screens without changing the drawing.

18.4 Event interest

Each object declares which events it wants: press, release, click, drag, hover enter and leave, key focus. The client sends only those, keeping input traffic small. This is filtering and routing only; nothing visual happens without the server.

18.5 Highlight

The server can set a "highlighted" or "selected" attribute on any object. The client renders it as a predefined colour remap or outline. It is a state the server sets with one small operation, not something the client animates.

18.6 Gestures

Gesture recognition (tap, double tap, long press, drag, swipe, pinch) is done once, in the server, from the raw touch points the client sends, and delivered to applications as typed events. Keeping it in the server keeps the client simple and the behaviour identical for every application.

19. Limits

Limits protect the client from a faulty or compromised server. They are set for this platform's capabilities, not a 1987 terminal's. Initial proposals, to be tuned by measurement:

20. The wire format

Messages from server to client are transactions of object operations; the contents of objects are ReGIS. The operations themselves need their own compact binary encoding, framed in websocket binary messages. A sketch of the operation set:

The renderer version must match the server's; a mismatch is a deployment error, not a negotiation.

21. The server

21.1 What it holds per session

  • A mirror of the client's display file: objects, masters, attributes and contents, no pixels.
  • The mapping between the application's names for objects ("fleet:7", "button:end-turn") and the client's integer ids.
  • Gesture recognition state, focus, hover state and event interest.
  • Pending transactions not yet sent.

21.2 What it does for every application

  • Validates every transaction against the types and limits, and against the mirror (ids exist, parents valid, depths in range).
  • Computes each transaction's damage and repaint cost from the mirror, and rejects transactions over the limits before sending.
  • Coalesces transactions that arrive faster than the client can take them: consecutive attribute changes to the same object merge; an object created and deleted before sending is never sent.
  • Manages masters: deduplicates identical drawings submitted as separate objects into a master with instances.
  • Routes events: resolves picked ids to application names, recognises gestures, manages focus and hover, and forwards only what the application asked for.
  • On reconnect, sends Reset and the whole display file from the mirror; the application does nothing.
  • Reports each transaction's cost back to the application.

21.3 One task per session

Each session is owned by a single asynchronous task holding its state and receiving work through a channel. No locks; updates are ordered.

21.4 Why the server stays simple

Because the client keeps the picture and repaints damage, the server never needs the client's pixels, never replays drawing commands, and never verifies by rendering. Its mirror is the client's display file, which is small. Correctness rests on the client's deterministic interpretation of the display file, tested by conformance tests, not on per-update verification.

22. The strongly typed API

22.1 One schema, three languages

The node kinds, attributes, operations and events are defined once, in Rust, and a schema generated from them produces types for TypeScript and Python. The three cannot drift apart; server and SDKs are built from the same version.

22.2 Invalid drawing is unrepresentable

  • Palette indices are a type with values 0 to 15.
  • Points are on-screen or object-local points with checked ranges.
  • Text is validated: characters from the selected set only.
  • Sizes, directions, line patterns, writing modes and transforms are enumerations of what is supported.
  • Tiles for loadable character sets are exactly ten rows of eight bits.
  • Object contents are built through a typed drawing builder, not raw ReGIS.

    SeriesAppend { name: Name, points: Vec<Point> },
    SeriesDrop { name: Name, count: u16 },
    SetMask { group: Name, mask: Name },
    Palette { entries: Vec<(PaletteIndex, Hls)> },
}

pub enum Event {
    Key { key: Key, modifiers: Modifiers, focus: Option<Name> },
    Pointer { device: Device, phase: Phase, target: Option<Picked> },   // mouse, pen or touch
    Gesture { gesture: Gesture, target: Option<Picked> },
    Message { message: Message },                                      // a handler's data, routed back
    Opened { reconnected: bool }, Closed,
}

pub struct Picked { pub name: Name, pub path: Vec<Name>, pub local: Point }
pub struct Transaction { pub in_reply_to: Option<EventId>, pub operations: Vec<Operation> }

22.4 Validation twice

The SDKs check values as applications build them, so mistakes surface early in the application's own language. The server checks everything again, because applications are untrusted.

23. Applications and the application protocol

23.1 Separate processes

Applications run as their own processes and connect to the server over a local socket. A crash in application code ends only that application; any language that speaks the protocol can be used; the server validates everything. Applications written in Rust can also link the server's crate directly and use the same types in process.

23.2 Messages

DirectionMessagePurpose
Application to serverRegister { app, version }Declares what it serves
Server to applicationSessionOpened { session, reconnected }A client connected
Server to applicationEvent { session, id, event }Typed input or a routed handler message
Application to serverTransaction { session, in_reply_to, operations }Changes, in reply to an event or unprompted (timers, data, other users)
Server to applicationRejected { session, reason }Invalid or over the limits; nothing changed
Server to applicationCost { session, bytes, repaint }What a transaction cost
Server to applicationSessionClosed { session }The client went away

On reconnection the server restores the client's screen from its mirror by itself; the application is told the session reconnected but need do nothing.

24. Programming styles

The server's interface is always typed transactions. SDKs offer styles that produce them.

24.1 Direct operations

// TypeScript: an industrial dashboard
const app = await connect({ app: "plant-monitor", version: 1 });
app.onSession(s => {
  s.transact(t => {
    t.defineMaster("valve", drawing(d => d.polygon(VALVE_OUTLINE, flat(1)).line(STEM, 2)));
    t.create("valve:12", "plant", instance("valve", { at: point(220, 180), remap: running, detectable: true,
                                                         on: [["click", msg("open", "valve:12")]] }));
    t.create("trend:flow", "trend-panel", series([], { colour: palette(9) }));
  });
  s.onEvent(e => {
    if (e.kind === "message" && e.message.name === "open") s.transact(t => t.set("panel:detail", { visible: true }));
  });
  setInterval(() => s.transact(t => {
    t.seriesAppend("trend:flow", [point(nextX(), flowY())]);
    t.setText("label:flow", `FLOW ${readFlow()} L/S`);
  }), 1000);
});

24.2 Declarative views

The application describes the whole screen as a function of its state; the SDK compares each description with the previous one in the application's process and sends only the resulting operations, as React does for the browser. Names identify objects across descriptions.

24.3 Immediate mode

24.4 Components

Large applications can build screens from function components with props and names; unchanged components are not re-sent to the server. This is an SDK layer.

24.5 Handlers as data

Handlers are messages, not functions: on: [("click", Message("open", "valve:12"))]. They cross the process boundary unchanged, behave the same in every language, and make applications testable without a client.

25. Events from client to application

  1. The client picks the topmost detectable object under the pointer or touch, if the object asked for that kind of event, and sends the event with the object's id, path and local position.
  2. The server resolves ids to the application's names, applies gesture recognition to touch, tracks hover and focus, and turns handler-bearing objects' events into Message events.
  3. Events bubble up the path: the object, its group, the viewport, the screen, until a handler takes it.
  4. Keys go to the focused object; focus moves by click and by keyboard navigation in tree order unless set.
  5. For immediate feedback, the application's reply can set a highlight in the same transaction as any heavier change; the client applies all of it at once.

26. The update loop

Every cause of change (input, timers, data, other users) reaches the application as a message and leaves it as a transaction. The server sends transactions in order; if the client's connection is slower than the changes arriving, the server coalesces pending transactions into one before sending, so a slow link receives the net change rather than a backlog. Because the platform has no acknowledgement protocol (section 2), flow control relies on the websocket's own backpressure: the server sends when the socket accepts more data, and coalesces while it does not.

27. Keeping pictures small

Object contents are ReGIS, and how ReGIS is written determines its size. Work on the test corpus established the techniques (recorded in REGISOPTIMISATION.md), with measured results:

  • Smooth shading as one dithered polygon fill per tone band, using loaded 8 by 10 dither tiles and replace-mode writing: three paintings went from 5.1 to 6.4 MB to 69 to 106 KB, 57 to 88 times smaller.
  • Pictures designed for size from the start: fifty paintings averaged 60 KB (largest 138 KB), against 5.7 MB for the naive method; all rendered complete.
  • The minifier removes redundancy losslessly: under 1 percent on carefully encoded ReGIS, 7 to 34 percent on naive or hand-written ReGIS.

The typed drawing builder applies these techniques when building object contents, and the minifier runs on every object's ReGIS before it is sent. In the platform, size also falls structurally: shapes become masters sent once, changes become attribute operations and edits in place, and charts become series objects.

28. Worked examples

Byte counts are estimated.

28.1 Pressing a button

The button is an instance of a button master with a colour remap. Pressed: one Set of its remap to the pressed colours, about 10 bytes. Its label is a text object; changing it is one SetText.

28.2 Moving an object over a detailed background

A fleet marker instance moves across a shaded nebula. One Set of its position, about 10 bytes. The client repaints the old and new areas from the display file: the nebula tiles under them, clipped internally, and the marker at its new place. Nothing is resent.

28.3 A dialog over a busy screen

A dialog is a viewport group defined once and hidden. Opening it: one Set of visibility and its text objects' strings. Closing it: one Set. The client repaints what was beneath from the display file. This is everything save-unders tried to do, with no saved pixels.

28.4 Typing into a field

The field is a text object. Each keystroke: one SetText with the new string, plus a caret object moved by one Set, about 20 bytes.

28.5 Scrolling a list

The list is a viewport whose children are row objects. Scrolling by a row: one Set of the offset; the application deletes the row that left view and creates the row that entered, about 60 bytes in all. The client repaints the viewport's area.

28.6 A live trend

A trend line is a series object. Each second: one SeriesAppend and, once the window is full, one SeriesDrop, about 15 bytes. The client repaints the line's area.

29. A strategy game, turn by turn

The Quiet Meridian, an original space strategy game in the test corpus, has 128 stars, six species and 20 screens averaging about 14 KB of ReGIS each (measured). On the platform, with estimated costs:

Compared with the earlier plain-ReGIS design (section 33), every change is an order of magnitude smaller, and switching between screens costs a visibility change once each screen has been defined.

30. Fast action games

30.1 Sprites are instances

A sprite is an instance of a master at a high depth. Each tick, the server sends position sets for everything that moved, creates new objects (bullets, sparks) and deletes finished ones. The client repaints the old and new areas from the display file, which is what sprite hardware did: nothing is ever burned into the background.

30.2 Bytes per frame

A busy shooter with a ship, twelve enemies, thirty bullets and a few explosions: about 45 position sets, a few creations and deletions, and a score text set, roughly 600 bytes a frame (estimated): about 18 KB a second at 30 frames a second, or 36 KB at 60.

30.3 No local animation

Every movement is sent by the server each tick. The server runs a fixed-rate game tick for such applications and coalesces late frames, sending only the newest positions.

30.4 Latency

LinkInput to screen
Same machine or local networkAbout 5 to 15 ms plus one frame
Same cityAbout 20 to 40 ms
Across a continentAbout 60 to 100 ms
Across an ocean150 ms or more

Strategy, puzzle and arcade games fit well at local or regional latency; competitive twitch games across long distances do not, because of the round trip, not the drawing.

31. Memory and computation

31.1 Server

Per session the server holds the display-file mirror (object structure and ReGIS contents, typically 20 to 150 KB, estimated from corpus screen sizes), the name map and routing state. No pixels. Tens of thousands of sessions fit on one ordinary server; identical masters and drawings can be shared between sessions by reference. Per transaction, the server validates, updates its mirror, computes damage bounds from object bounds, and encodes: work proportional to the operations, typically microseconds.

31.2 Client

The client holds the display file and its screen: two 800 by 480 pages at one byte per pixel (768 KB) plus the display file. A full-screen repaint of a detailed painting takes 27 to 53 ms on the development machine (measured, for the existing renderer drawing a whole 53 to 88 KB painting); typical damage repaints cover small areas and cost far less. Repaint cost per transaction is bounded (section 19).

31.3 Compared with live server interfaces

The server's per-session state is comparable to a LiveView connection (tens to hundreds of KB), because it holds a retained description, not pixels. The earlier design's per-session cost of about 0.9 MB of shadow pixels no longer exists.

31.4 Persistence

Application state is the application's responsibility. The server's mirrors are rebuilt by the application on demand after a server restart (the session is reported as reconnected and the application re-describes its screen). A client that reconnects is sent Reset and its whole display file. No resumption protocol is used (section 2).

32. Security

  • The client parses the operation encoding and ReGIS with strict, bounded parsers, enforces the limits of section 19, and runs no code from the server. The renderer already has no unsafe code, no panics on untrusted input and a record of twelve security issues found and fixed.
  • The server validates every client message (sizes, ranges, rates) and authenticates sessions with unguessable, expiring tokens issued by the deployment's authentication system.
  • Applications cannot send raw ReGIS or exceed limits: every transaction is typed, validated and costed against the mirror before anything is sent. Past a rejection threshold, a session is closed.
  • Sessions are isolated: each is owned by its own task; shared masters are immutable once shared.

33. The earlier design, and why it changed

The first version of this proposal kept the client as a plain VT340 ReGIS terminal. Because such a terminal remembers nothing and cannot remove anything, all intelligence had to live in the server:

  • a shadow terminal per client, an exact copy of the client's renderer fed every byte sent, to know what each client displayed (about 0.9 MB of pixels per session);
  • labelled command spans with exact pixel footprints measured by the shadow terminal, and a footprint index to find which commands drew an area;
  • replay with transitive closure to remove anything, repainting every command touching the damage and every command touching those, which only stayed local if backgrounds were cut into small tiles;
  • verification of every update by rendering, expensive enough that it had to be limited to damaged regions;
  • bit-plane overlays, complement-mode transients, palette tricks and page flips as cheap native ways to remove things;
  • a pixel-difference fallback with dither recognition;
  • session tiering, compression and memory mapping to keep the pixel copies affordable;
  • acknowledgements, state hashes and resumption to survive reconnects.

Every one of those mechanisms existed to compensate for a client that keeps no structure. Once the decision was made that the platform controls the client with no fallback, the research of section 7 points straight at the alternative: put the retained structure in the client, as display processors, Tektronix terminals, X compositors and Flash all did. The server then needs no pixels, no replay, no verification by rendering and no plane tricks, and every change becomes an operation of a few bytes.

36. Decisions needed

  1. The schema format and code generator for TypeScript and Python types.
  2. The server's crates: an asynchronous runtime, websockets and serialisation. The renderer workspace uses no external crates, and each needs approval.
  3. The binary encoding of client operations, specified exactly.
  4. Where the platform lives: extensions in the renderer repository, server and SDKs in new repositories, or one repository.
  5. The limits of section 19, confirmed or adjusted.
  6. Authentication: which system issues session tokens.
  7. The first two applications that prove the design, for example an industrial dashboard and the strategy game.

37. Implementation plan

  1. Specify the display file: object kinds, operations, attributes, damage rules, limits and the binary encoding, with a conformance suite of display files and their expected pixels.
  2. Client display file and repaint: objects, masters, instances, depth, hierarchy, visibility, transforms, internal clipping and damage repaint, built on the existing renderer.
  3. Client viewports, masks, text and series objects, highlight and colour remapping.
  4. Client input: pushed events, picking, hit shapes, event interest.
  5. Server skeleton: websockets, sessions as tasks, the display-file mirror, validation, limits, coalescing, reconnect by resend.
  6. Schema, generated types and one SDK with direct operations.
  7. Two real applications, measured for bytes, latency and memory against the estimates in this document.
  8. Gesture recognition, focus and keyboard navigation in the server.
  9. Declarative and immediate-mode SDK styles, and the second language's SDK.
  10. The typed drawing builder with the compact painting techniques, and master deduplication in the server.

38. Testing

  • Conformance: every display file in the suite produces exactly its expected pixels, on every build of the client.
  • Repaint equivalence: for random sequences of operations, the screen after incremental damage repaint equals a full redraw of the display file. This is the property that replaces per-update verification, and it runs in debug builds and a long randomised test, as the renderer's gate does today.
  • Mirror equivalence: the server's mirror after any sequence of transactions equals the client's display file.
  • Limits: operations at and beyond every limit, from both server and application sides.
  • Protocol robustness: malformed, oversized and out-of-order messages.
  • Applications without a client: feed events, check transactions.
  • Load: memory and processing per session at realistic mixes.
  • Local gates: formatting, strict lints, the no-panic lists, tests and documentation, enforced by git hooks.
